# Aster Time：时间账本与预算设计

日期：2026-11-15。状态：产品设计草案，已加入手动开始与到期自动停止，尚未实现。

首版范围与工程决策见
[V1 决策与验收](time-management-v1-decisions.md)。本文描述产品方向；涉及 V1 范围、统计口径、计时来源、迁移与兼容时，以该决策稿为准。

## 1. 产品决策

用户希望像管理财务一样管理时间，目前没有明确的单项痛点或界面偏好。默认方案是：以时间账本为基础，形成“记录 → 对账 → 看分布 → 定预算 → 安排 → 再记录”的循环。

推荐先作为 Aster 内的独立 Time 模块开发，复用登录、工作区、任务引用和已有计时能力。Time 有自己的活动分类、账本和预算，覆盖睡眠、休闲、社交等全部生活活动；活动不要求绑定任务。Grok
bot 作为自然语言入口。以后如需独立产品，可以抽出这个领域模块。

产品长期回答三个问题：

1. 我的时间实际花在哪里？
2. 这样的分配是否符合我的意愿？
3. 接下来想调整哪一小部分？

是否适合用户，需要通过实际使用验证。设计不以全自动、满日程或记录完整度作为成功标准。

## 2. 财务模型如何迁移

| 财务概念 | 时间模型               | 边界                                     |
| -------- | ---------------------- | ---------------------------------------- |
| 可用资金 | 某个日期区间的时间容量 | 时间不断流逝，未用的未来空档不能跨日结转 |
| 流水     | 实际活动及持续时间     | 支持计时、补记、估计；保留来源与精度     |
| 科目     | 生活领域分类           | 默认少量分类，项目和任务另作关联         |
| 预算     | 希望保留或限制的时间   | 同时支持下限、上限和目标范围             |
| 账单核对 | 每日时间线对账         | 核对空白、异常计时和冲突，允许跳过       |
| 报表     | 分布、变化和预算偏差   | 必须同时呈现未记录部分，避免伪精确       |

常规完整日有 24 小时，但系统按用户时区的实际日界计算，不硬编码每天的秒数。当天尚未发生的时间是“未来”，已经过去且没有活动证据的时间才是“未记录”。

## 3. 日常流程

### 初次使用

默认采用 Asia/Shanghai，允许修改。提供睡眠、工作/项目、学习、运动、生活事务、通勤、休闲、社交八个可编辑分类；“未记录”是系统状态，不是活动分类。

初次使用只介绍记录和每日对账。先收集真实样本，再邀请用户设预算。作息模板只用于规划或生成候选，不自动写成已发生记录。对账时把“常规作息待确认”和“其他空白”分组；支持一句“昨晚睡眠照常”确认当前展示的候选，不额外增加每天必做的晨间操作。未确认候选仍计入未记录。

### 随手记录

记录入口支持三种方式：

- 当下开始：“开始研究 Aster 的时间模块。”结束或切换时停止当前主活动。
- 事后补记：“刚才 20:00 到 20:45 在散步。”解析后直接记账，并返回可撤销回执。
- 大致补记：“昨晚大概看了一小时书。”保留估计时长；没有足够信息时不编造精确起止时间。

明确且无冲突的输入直接执行；日期、活动指向或时间范围有实质歧义时只问必要的一句。bot 回复显示解析后的日期、活动、时长和分类。消息重试不会重复记账。

Aster 的任务操作可关联工作和项目活动。Time 启用后，新计时统一经过 Time 服务；普通活动也能独立开始和停止，无需先创建任务。生活领域按“本次明确指定 → 任务覆盖 → 最长项目路径规则 → 有优先级的标签规则 → 未分类”选择。规则未命中不阻止记账，也不必每次询问或调用模型。

### 手动开始，到期自动停止

用户已明确选择：预估 60 分钟、计划 14:00 开始、最晚 15:00 停止，若 13:40 提前开始，应在 14:40 停止。

任务的“本次计时安排”包含三个独立字段：预计用时（本次额度）、计划开始（只提醒）、最晚停止（硬性时刻）。均不复用 Taskwarrior 的截止日期。只有点击开始或明确对 bot 说开始才计时，允许提前或晚于计划开始；到点提醒、打开页面、服务器恢复和上一项结束都不能自动开始。

自动停止时刻取“实际开始 + 本次剩余额度”与“最晚停止”中的较早者。只设置其中一个限制时使用该限制；未设置任何限制的普通活动沿用防忘停检查点。预计用时与最晚停止有冲突时，界面提前显示此次最多可计时多久，不悄悄延长截止时刻。

| 实际操作（预计 60 分钟，计划 14:00，最晚 15:00） | 结果                                     |
| ------------------------------------------------ | ---------------------------------------- |
| 13:40 提前开始                                   | 14:40 自动停止                           |
| 14:00 开始                                       | 15:00 自动停止                           |
| 14:30 才开始                                     | 15:00 自动停止，本段最多 30 分钟         |
| 一直没开始                                       | 到期标记安排未开始，不产生时间记录       |
| 15:10 才想开始                                   | 原安排已过期；用户明确调整安排后才能开始 |

暂停不消耗额度，但绝对结束时间继续逼近；再次手动开始沿用同一安排的剩余额度，不重新赠送完整时长。例如 14:00 开始、14:20 暂停、14:40 继续，仍在 15:00 停止，总计时 40 分钟。需要更长时间时可明确增加额度；若要越过最晚停止，还须明确修改该时刻。

这能限制忘停造成的误记范围，不能证明期间一直在做。自动停止的记录标为“已停止 · 待核对”，先保留在草稿中；此前确认过的部分仍计入正式统计。用户可一次确认“这段没问题”、改为实际提前结束，或事后补记确实超出的投入。自动停止只停止 Time 时钟，不完成任务，不改任务截止日期，也不启动下一项。

开始按钮应明确显示“开始 · 最晚 14:40 停止”；运行中显示预计停止时刻与剩余时间；结束后提供“确认这段 / 修正结束 / 增加时间并手动继续”。不因忽略通知自动延时。服务器保存停止规则，即使网页关闭也限制计时，服务中断后按原停止时刻补结算；实际通知送达可能晚于该时刻。

### 晚上对账

提供一次可关闭的每日提醒，目标是约一两分钟完成。主动提醒由 bot 侧调度和发送；Aster 仅提供只读对账摘要。未接通 bot 调度时，通过网页打开时的对账卡或主动询问使用同一摘要，不声称后台已能主动发消息。展示当天时间线，只突出有必要处理的空白和明显异常：

> “今天有一段较长的未记录时间：19:00–21:00。可以补一句，也可以保留空白。”

用户说“吃饭和看电影，大概各一小时”，V1 保存两条带时间窗口的待定位估记，暂不增加时间线覆盖。有窗口的估记作为注释靠近该时段展示，点开可定位；没有窗口的放独立列表。注释不占据时间容量，也不自动拆分空白。用户之后确定区间时，原记录转为已定位记录，不再保留一份重复估记。窗口内多分类分配推迟到后续版本。记不清可以跳过。漏记多天后可直接从今天继续，不强迫清理历史。

每天不追求记满 24 小时，也不将空白自动归为娱乐或浪费。允许按时段粗记，不要求每次拿手机或倒水都记录。

### 每周看一次分布

周报的主图仅统计已核定、已定位且无冲突的区间，各领域之和等于时间线覆盖；其余显示为“未核定”，包括完全空白和待核对计时。运行中的暂计、忘停草稿与待定位估记均单列，不加入主图、不扣减空白、不计为预算已投入。例如完整一天覆盖 16 小时、未核定 8 小时，另有约 1 小时阅读待定位，仍是 16 +
8 = 24，不是 17 + 8。周中报表必须标明只统计截至当前时刻。

AI 先给事实，再提出最多一个可操作的调整，例如：

> “本周已记录学习两小时。你设的目标是四小时。下周是否保留两个一小时的晚上？”

记录不足时说明“不足以判断”，不以局部数据声称整周时间分布。没有用户设定的偏好，不给活动贴好坏标签。

### 从真实样本生成预算

预算有三种语义：

- 保护：希望每周为学习、运动或陪伴保留多少时间。
- 限制：用户主动希望某项活动不要超过多少时间。
- 观察：只追踪，不设目标。

固定占用、生活需要和用户选择的休息时间先占容量，再分配可调整的部分，并保留机动时间。所有数字都允许调整，不能拿统一的“高效日”模板替用户决定生活。

例如，一周可调整时间估计为 12 小时，可以先分配开发 5 小时、学习 3 小时、运动 2 小时，留下 2 小时机动。这只是产品示例，不是对用户实际作息的判断。

预算目标、已排计划和实际投入分列显示。若目标之和超过可用时间，明确显示冲突，让用户选择取舍。

### 需要时再安排到日历

周预算可以停留在“这周给学习三小时”，不必强制决定每天几点开始。只有需要保护具体时段时才生成计划块。

固定约定锁定；可移动的计划可提出调整建议。临时事件占用时间后，优先利用机动时段，仍放不下则展示缩短、延期或取消某项安排的选择。不能默默压缩休息、移动硬性约定或延长用户设置的结束时间。

保留原计划和调整记录。未执行的计划不转成实际活动；没有完成的时间块也不等于关联任务失败或逾期。

## 4. 页面与客户端范围

侧边栏新增“时间账本”分组，保留现有任务“今天”和“焦点”入口。V1 只提供 Web 页面与 MCP/bot 能力；桌面和 TUI 不新增时间页面，但需要验证既有任务计时接口兼容。

### 今日时间线（V1）

最重要的日常入口：当前活动、开始/结束/补记、当天时间线、待核对空白。常规作息候选单独折叠展示。未来加入规划时，再区分实际活动与计划、显示可安排容量。

### 本周分布（V1）

展示时间按领域的分配、未记录与待定位估记。选择某个领域可以查看相关活动、项目和任务。预算目标、已安排和实际投入的比较在 V2 增加。

### 时间设置（V1）与时间预算（V2）

V1 的设置页只放分类映射、时区、作息候选和提醒。V2 的“时间预算”设置希望增加或减少投入的领域及每周目标。只保存用户明确选择的偏好，不从一次行为推定长期价值观。

手机以快速操作和 bot 为主，网页承担查看分布、调整时间线与预算。复杂编辑不要求全部通过对话完成。

## 5. 时间账本必须成立的规则

1. **计划和实际独立。**
   日历会议、重复作息和 AI 预测只能产生计划或待核对候选。确认实际参加后才入账。
2. **主活动不重复计费。**
   同一时刻只能有一项计入总时间的主活动。V1 的“通勤听课”选一个主分类，另一项写备注；伴随活动的独立统计后置。
3. **冲突显式处理。**
   V1 遇到区间重叠先保留草稿并返回冲突记录，可编辑边界或撤销误记后重新提交；不提供自动覆盖、复杂拆分或伴随活动选项。源数据异常时保留冲突待核对。
4. **粗略记录保留粗略性。**
   无精确起止的时长记录保存在日期或时间窗口内，作为未定位记录呈现。对账后才能认定它填补哪段空白；不能与时间线记录盲目相加。
5. **已覆盖不等于全都精确。**
   分别显示已确认、估计、待核对和未记录。未定位记录展示为另有估计，避免把它假装成精确覆盖。
6. **忘停计时可修正。**
   计时中的时长先作暂计；设置额度或最晚停止的安排按规则自动停止并待核对，不因忽略提醒继续累加。未设置停止限制的普通活动，默认在 60 分钟检查点询问一次，可按活动调整。已明确确认的部分进入正式统计，未确认部分隔离；自动停止不能证明实际持续投入。睡眠使用独立作息策略，提醒可关闭。
7. **跨日不复制。**
   一条活动可以跨午夜，报表按当地日界拆分持续时间，仍关联同一活动。保存绝对时间及用户时区。
8. **计时结束不等于任务完成。**
   Time 不因时间块结束、预算用完或日程调整而改变 Taskwarrior 的 UUID、状态或截止日期。
9. **数据故障不是零投入。**
   来源不可用时显示同步状态；不清空既有记录，不将缺失数据参与正常趋势比较。
10. **休闲也有正当位置。**
    不设置默认“浪费时间”分类，不用总工作时长、连续打卡或记录完整率给用户评分。

## 6. 系统边界与数据归属

| 系统         | 负责的事实                                 | 与 Time 的关系                                                    |
| ------------ | ------------------------------------------ | ----------------------------------------------------------------- |
| Aster 任务域 | 要做什么、项目、任务状态                   | Time 引用任务 UUID，复用名称和项目，不复制任务主数据              |
| Time 域      | 实际活动、计划块、时间预算、对账修正       | 拥有启用后的新计时及独立数据库，是时间账本的唯一查询入口          |
| Timewarrior  | 历史任务计时区间、可能仍存在的旧 hook 副本 | 仅作历史快照导入来源；不持续双向同步，不把启用后的副本再计入 Time |
| Bills        | 金钱流水                                   | 后续可按明确关联的项目或事件并列展示金钱与时间投入                |
| Grok bot     | 用户指令入口                               | 调用领域接口，解释结果，不独立维护另一份账本                      |

已核对本地任务动作、精力计算及客户端拦截、组织数据读写、导航与 MCP 文档。未验证线上部署、Bills 或 Grok
bot 的实际接口。MCP 文档中的“bot 部署在 dmit”是条件示例，不是已部署的证据。

已有精力值由活动启动和计时时长等规则计算，是应用内部指标，不是对人的实际精力测量。Time 模式下将精力降为展示指标，解除服务端与客户端的耗尽拦截；计时是否可写由 Time 自身健康状态决定。Time 使用用户时区 00:00 日界；原精力 06:00 周期单独标注，不共用统计总数。

Time 原生计时只写自己的事务存储，任务引用不自动修改 Taskwarrior。现有 task_start/stop 等动作经兼容协调器接入同一 Time 引擎；跨系统操作用持久化操作日志与结果核对处理部分成功，不宣称外部命令和数据库写入是一个原子事务。具体语义、故障和切换规则见 V1 决策稿。

所有客户端的任务行与详情仅为当前 Time 活动外推“本段暂计”，正式合计只使用已核定投入；任务保留“进行中”标记时也可以没有运行中的时钟。提醒关闭或未送达不会把草稿自动变成实际投入。旧任务备份恢复会暂停并核对受影响的时间关联，不自动续计、不删除时间历史。发布备份必须包含独立 Time 数据库，备份失败不得继续切换版本。

Time 活动使用自身生成的 UUID。历史导入使用冻结的快照批次和切换截止时间，保留原始记录、来源与导入清单；重复导入同一快照无效果。Timewarrior 的 @id、任务 UUID + 开始时间都不作为跨修改的永久身份。历史修订在 Time 内完成，不回写 Timewarrior；不同快照的重叠范围需要预览核对，不能直接累加。

Time 数据与策略保存在独立的 time.sqlite，不进入 organization.json，也不共用 organization.revision。接口按日期范围查询，Time 日常读写不触发全量 task/timew 导出。独立备份恢复与运行时验证属于上线条件。

与财务的结合后置。例如某个学习项目可以并列展示“花费金额”和“投入时长”。消费发生时间只能帮助回忆，不能由一笔餐费推断用餐两小时，也不能默认把所有生活时间折算为金钱。

## 7. 最小数据模型与接口边界

核心对象：

- Activity（V1）：实际活动；分类、可选 task/project 引用、时间范围或待定位估记、来源、精度、核对状态、修订信息。伴随关系后置。
- TimingPlan（V1）：用户手工设置的一次计时安排；可选任务引用、预计额度、计划开始、最晚停止、暂停/重开后的已用额度及版本。关联多个计时段，不自动开始或自动排程。
- PlanBlock（后续）：未来安排；起止时间、可移动性、可选任务引用、计划修订。与 Activity 分开保存，可建立执行关联。
- TimeBudget（V2）：周期、领域、目标语义、目标时长、有效日期；目标变化保留版本。
- TimePolicy：时区、活动分类、作息约束、提醒及可用时段。作息模板不是实际活动。
- ImportBatch / SourceRecord：冻结的导入批次与原始来源，不承担持续双向同步。
- Operation：写入幂等键、规范化输入、持久化结果及跨系统待核对状态。

bot 的初始能力包括：保存/修改本次计时安排、明确开始/暂停/结束、补记/修正/撤销、读取日账/周账及对账摘要、确认作息候选、查询写入结果。自动停止由服务端执行，bot 负责呈现回执与通知。周预算工具在 V2 添加，自动排程建议更后置。

写入接口支持幂等键、版本检查和撤销；自然语言解析与执行分开。LLM 解释用户输入、给出分类和建议，程序负责日期计算、重叠检查、统计和最终持久化。LLM 不能自行补造活动、认定会议出席或绕过容量约束。

平台编辑消息时，bot 将编辑关联到原记账结果并发起新的版本化修正，不能用同一个 messageId 再创建一笔活动；跨日编辑保持原日期上下文。删除聊天消息不会自动删账。

## 8. 开发顺序与使用验证

### 第一阶段：把账记起来

先完成独立存储、单活动计时、幂等与任务兼容底座，再交付 Web +
MCP/bot 的计时安排、手动开始/暂停/结束、到期自动停止、区间补记、待定位估记、作息候选确认、对账时间线、周分布、修正撤销。历史导入是独立的可选准备步骤，不阻止从今天开始使用。

V1 明确不做：伴随活动统计、窗口内多分类分配、复杂重叠拆分 UI、预算、自动排期、设备监控，以及 Desktop/TUI 的新时间页面。旧客户端必要的协议/拦截兼容不属于可省略范围。

验收至少覆盖：计时开始/停止生成一段活动；消息重试与切换竞争不双算；跨日正确拆分；精力为零仍可记账；估记不让一天超过总容量；睡眠候选不自动入账；未知操作先核对；独立备份可恢复；任务 UUID、状态和截止日期不因 Time 原生操作变化。完整列表见 V1 决策稿。

### 第二阶段：从账本长出预算

增加领域预算、目标/计划/实际比较、固定约束、机动容量与每周回顾。先使用一周，再选择少量真正想改变的分配。

### 第三阶段：按需辅助安排

增加可选计划块、冲突提示和可撤销重排。再根据真实使用决定是否需要日历、屏幕使用、睡眠或运动数据接入。自动采集默认只提供候选；采集范围可选，不靠全设备监控才能运行。

前两周验证问题：记录是否足够省事；周报是否让用户看懂时间分布；是否据此作出一次有价值的调整；漏记后是否还能自然回来。每日维护约一两分钟是设计目标，实际负担需测量。若用户更喜欢晚上回顾，就降低实时计时的地位。

## 9. 外部设计参考

- [Sunsama：Daily Planning](https://help.sunsama.com/docs/getting-started/basics/daily-planning-the-basics/)：先看工作量、决定什么可以等待、安排顺序并设置结束时间。借鉴它的容量与收尾流程。
- [Sunsama：Timeboxing](https://help.sunsama.com/docs/usage-guides/timeboxing/)：任务可以对应多个工作时段；日程灵活时可以不强制逐项锁定时间。借鉴任务与时段分离、安排可选的做法。

以上是产品交互参考，不作为某种方法一定适合用户的证据。本设计的重点是生活时间账本与预算，是否增加具体安排功能由使用验证决定。
