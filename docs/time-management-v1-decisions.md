# Aster Time V1：评估处理、技术决策与验收

日期：2026-11-15。状态：设计决策，已加入用户确认的手动开始与到期自动停止规则，尚未实现或部署。关联：[产品设计](time-management-design.md)。

## 1. 评估结论与证据边界

采纳评估提出的睡眠候选、统计口径、分类映射、存储隔离、首版裁剪、导航命名和提醒归属问题。进一步核对发现：

- `modules/server/src/task-actions.ts`
  的 start 分支确实会因计时不可用和精力耗尽拒绝操作。
- `modules/web/src/app/hooks/use-task-completion.ts` 和
  `modules/desktop/src/ui/use-task-list-actions.ts`
  也有前置拦截。仅修改服务端不能解决全部问题。
- `modules/core/workspace/energy.ts`
  使用运行进程本地时间的 06:00 日界；Time 需要独立的用户时区日界。
- `organization-store.ts` 全量写 JSON、共用 revision；`organization-service.ts`
  的 workspace 读取和 change 前置读取会加载任务及 Timewarrior。Time 不复用这条读写链路。
- “约五小时耗尽”只是近似；精力还受启动次数和加成影响，不能写成固定计时上限。
- Taskwarrior 的多个任务可有 start 标记，不能据此认定用户同时实际从事了多项活动。
- MCP
  README 只说“如果 bot 部署在 dmit，可以直连 socket”，并不证明现有 bot 的位置、调度或推送能力。
- Timewarrior 的 @id 是位置索引。`taskUuid + start`
  也会因修改开始时间而改变，且活动未必有关联任务，不能作为不可变身份。
- `native-restore.ts` 的 `sqliteSnapshot()` 已使用 `DatabaseSync`、`backup()` 和
  `PRAGMA integrity_check`；`deploy/deploy.sh` 也已在线备份 Taskwarrior
  SQLite，但未覆盖 Time。运行时支持已有代码先例，仍需验证实际运行进程。
- Web 的 `taskTrackedSeconds()`、TUI 的 `taskMetaSpans()` 和 `inspector()`
  会从 task.start 推导跳表，必须连同列表、详情与操作按钮一起适配。
- `backupRestore.applyPrepared()` 会在 `gate.exclusive()`
  内替换原生数据库；`repair()` 当前只处理 prepared
  manifest。恢复后的 Time 核对需要覆盖成功、回滚和进程崩溃后的启动修复。

未检查生产服务器或 Grok bot 仓库；以下方案不等于线上现状。

## 2. 固定首版范围

用户闭环：开始/结束或补记 → 当天简单对账 → 看一周分布。新页面只做 Web，新对话能力通过现有 MCP/Socket 提供。

V1 包含：单主活动计时、手工计时安排与到期自动停止、区间补记、独立待定位估记、修改/撤销、分类默认映射、睡眠候选确认、日期范围查询、周分布、独立备份，以及必要的任务接口兼容。手工计时安排是本轮用户明确新增的范围，不包含自动排程或周预算。

V1 排除：伴随活动单独统计、窗口内多分类时长分配、自动拆分冲突、双向 Timewarrior 同步、预算、排期、设备监控、Desktop/TUI 新时间页面。历史批次导入可晚于首次启用；用户可以直接从今天开始。

正确性底座不会因裁剪 UI 被移除：重叠检测、幂等、未知写入核对、跨日计算、撤销冲突检测和备份必须保留。

## 3. 统计只采用两种口径

### 已定位账本

一条记录有明确的起止区间。起止可由计时获得，也可由用户大致指定；后者保留“估计边界”标记。所有区间按用户时区裁切到报表范围，并采用半开区间
`[start, end)`，相邻端点不算重叠。

在过去时段内，互不重叠、已核定的区间累计为覆盖 C；报表已过去的总容量为 T；未核定 U
= T - C。所有领域之和为 C，并始终满足 C + U =
T。U 包含完全空白以及有计时草稿、尚未确认的部分；草稿和估记是它的附加说明，不是另一份可相加的时长。运行中的暂计单列，未来不算空白。

活动的时间边界精度（准确/估计）与核定状态分开：用户确认“大约半小时”可以进入正式账本，但应保留估计标记；计时器一直运行不等于期间持续从事了该活动。开始按钮只确认开始时刻，正常且未触发疑似忘停的明确停止可确认本段；疑似忘停、自动切换截断的未确认段先留草稿。批量核对可在一次日对账完成，不要求每段额外弹窗。

### 待定位估记

“昨晚看书约一小时”没有明确区间，保存日期/窗口、时长和原话，放在独立列表。既不加入主图，也不扣减未记录，不进入未来的预算实际投入数。

完整一天示例：已定位 16 小时、未记录 8 小时，另有“阅读约 1 小时待定位”。用户将原估记定位到未占用的 21:00–22:00 后，同一记录转为区间：已定位 17、未记录 7、待定位 0。不能新增一条区间后遗留原估记。

V1 不把“19:00–21:00 吃饭和看电影各一小时”自动填满两小时窗口；保存两条估记即可。用户不愿精确回忆时可长期保留；缺少覆盖不触发惩罚或清空。

遇到区间冲突返回相关记录并保留输入，用户调整边界或撤销误记后再保存。被拒绝的草稿不进入任何实际总量。待定位估记可能与已定位记录重复，因此不能把两者相加为总投入。

### 带窗口的估记如何展示

估记可带成对的 `windowStart/windowEnd`，另存
`estimatedSeconds`；窗口只表达“可能发生在这里”，不是实际区间，也不预留时间容量。有窗口的估记作为注释卡靠近该时间段显示，标明“约 X 分钟 · 待定位”，不画成按时长占据空白的已记账色块。窗口与已记录活动重叠时仍保留注释，不暗示估记一定发生在空白中；无窗口的估记放在独立列表。

点击注释只打开这一条记录的定位表单。提交时携带原 activity
UUID、版本和明确起止，事务内重新验证重叠，再将原记录转为区间；其他估记不自动拆分或定位。跨日/跨多个空白槽的同一估记按 activity
UUID 去重，周报不能重复累计。取消编辑不改变记录。V1 不新增自动拆分 UI。

## 4. 睡眠和分类降低日常操作量

作息模板按用户明确设定的时间生成“常规作息待确认”候选，和“其他空白”分开显示。不要把其他空白直接称为已知清醒时间，因为模板不能证明是否醒着。

用户在一次日对账中点“睡眠照常”，或对当前候选说同样的话，才将该日期的候选转为已定位估计记录。回执显示明确的日期与区间。存在冲突时先核对；不能用睡眠候选自动覆盖疑似忘停的工作计时。

候选有稳定的日期、模板版本和候选标识；重复确认只产生一条活动。模板变化不改历史，忽略候选也不追发提醒。不另设必做的晨间确认。

分类规则从明确到一般：本次指定 → 任务级覆盖 → 最长项目路径匹配 → 按显式优先级选择的标签规则 → 未分类。项目匹配遵循路径段边界，`Aster`
可匹配 `Aster.Time`，不能误匹配 `AsterOther`。

例如
`Aster.* → 工作/项目`、`Learn.* → 学习`。落账时保存分类、规则版本和项目名称快照；修改映射默认只影响未来，历史重分类需要单独预览操作。不会为每次计时调用模型或反复询问分类。

## 5. Time 拥有新计时，Energy 退出准入控制

以 workspace 为范围，Time 最多有一条打开的主活动。开始下一活动在同一个 SQLite 事务内关闭上一活动并创建下一活动，使用同一个服务端时间点。并发操作使用当前活动的版本检查；旧请求不能意外停止另一客户端刚启动的新活动。

Time 自己生成 activity
UUID，结束、修正、分类变化不会改变它。数据库持久化失败时不能向用户返回“已开始”。

Time 模式下，Energy 作为可选展示指标保留。删除服务端、Web、桌面共享模式中的“精力不足不能开始”逻辑；保留故障和数据完整性校验。通过服务端能力字段明确当前 timer
backend、是否存在硬性精力限制及 Time 可用状态，客户端不根据 energy.remaining 猜测权限。

Time 报表用用户时区 00:00 日界。Energy 保留 06:00 周期并显式使用相同配置时区、标明周期；Time 模式下其任务时长输入只来自同一账本中关联任务的已核定区间，不把计时草稿、睡眠、休闲或待定位估记算成精力消耗。既有精力状态保留，周期切换需按原规则初始化，不能删除用户历史。

不能只替换区间来源后原样调用旧精力算法：`calculateEnergy`
会对缺少区间的 task.start 补算时间，`liveEnergySummary`
也依赖活动数量。Time 模式必须停用这些基于任务 start 的兜底，当前活动只来自 Time 的单活动状态。切换当期若历史尚未导入，标明周期数据不完整并暂停剩余精力推算，不能将缺失历史视为零投入或自动恢复满格。

Time 页面显示实际活动时长；任务侧边栏明确标成“精力周期/任务投入”，避免和全生活的自然日合计混淆。

Timewarrior 不可用时仅历史导入/旧数据能力受影响，不阻止原生 Time 计时。Taskwarrior 不可用时仍能记录无任务活动；涉及任务动作的写入须返回真实故障。

### 5.1 全部客户端共用计时快照

服务端提供版本化
`TimerSnapshot`，通过独立 Time 查询和任务列表的轻量附加数据复用；不得为了获取它调用旧 organization 全量读取。以下为待实现契约，不代表现有字段：

| 字段                               | 含义                                                                                                                                                                                   |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `backend` / `contractVersion`      | `time` / `1`；非 Time 模式保持旧协议                                                                                                                                                   |
| `timeEpoch` / `taskDataEpoch`      | Time 恢复代次、关联任务数据代次；不一致的响应不能合并                                                                                                                                  |
| `state` / `sessionVersion`         | `ready / pending_reconcile / restoring / unavailable`；当前计时槽版本                                                                                                                  |
| `snapshotAt` / `liveUntil`         | 服务端 UTC 采样时刻、允许客户端外推的截止时刻                                                                                                                                          |
| `activeActivity`                   | 空或 `{ id, version, taskUuid, startedAt, state, confirmedThrough?, reviewDueAt?, provisionalSeconds, suspendAt?, timingPlanId?, autoStopAt?, limitVersion? }`；未确认段与正式投入分开 |
| `taskTotalsSeconds`                | 当前结果涉及任务截至 snapshotAt 的已核定投入，仅含活动已经确认的前缀；不含未确认的计时草稿                                                                                             |
| `coverageFrom` / `historyComplete` | 已知记录范围与完整性；缺少旧历史时不显示为完整生命周期总计                                                                                                                             |

每个任务行的正式值取
`taskTotalsSeconds[uuid]`，不在客户端累加。仅当快照 ready、活动 running 且其 taskUuid 等于该行 UUID 时，在旁边显示“本段暂计”，以
`activeActivity.provisionalSeconds`
加上收到快照后的单调时钟经过秒数，最多加到 liveUntil。客户端收到新快照时整体替换基础值，不叠加旧的外推值；暂计不能写回或混入正式总计。

初始 `liveUntil`
设为 snapshotAt 后 30 秒、存在的 reviewDueAt、autoStopAt 与查询固定结束边界中的最早值。客户端可每 15 秒刷新活动快照。达到 autoStopAt 必须显示已到停止边界，不继续本地跳表；失联时不得声称已经收到服务端提交成功。其他失联、页面休眠后恢复或核对/恢复状态停止外推，显示“待刷新/待核对”；不回退到 task.start 或本机墙上时钟计算。时间戳与截止上限由服务端提供，经过时间使用客户端单调时钟。

Time 模式下，缺失任务合计键表示未知，显示“—”；明确返回 0 才显示零。无任务活动仍可显示全局时钟，但所有任务行都保持静态。

必须修改的显示链路包括：Web `use-workspace-data.ts` 的跳表触发与
`taskTrackedSeconds`，`task-row.tsx`、`task-meta-chips.tsx`
及详情中的状态文案；TUI `view.go` 的 `taskMetaSpans` 与
`inspector`；桌面共享模式中的任务操作与时长显示。任务的“进行中”仍取 Taskwarrior 状态，“正在计时”及计时按钮行为取 activeActivity，两者不能复用同一个布尔值。

验收示例：先 task_start(A)，再 task_start(B)。A 显示已有核定投入及本次待核对记录，只有 B 显示本段暂计；有 start 标记不代表仍在计时。stop(A) 只停止 A 的任务标记，不让 B 的时钟停下。快照乱序返回时，按 epoch、sessionVersion 和 snapshotAt 拒绝旧结果；恢复后必须整份刷新。

### 5.2 防忘停：暂计、检查点与快速核对

废止“超过六小时才提示，仍把整段算进正式统计”的默认做法。计时器只能证明启动后经过了多久，不能证明人在持续进行该活动。方案降低误记和修正成本，不承诺无感知条件下百分之百自动还原真实活动。

本节作为未配置自动停止限制时的兜底：普通活动先以 60 分钟作为可调整的检查点默认值。明确设置“本次计时半小时”或最晚停止时刻时，采用 §5.3 的自动停止，不再只提醒后继续等待。任务的总体工作量预估只有被用于本次额度时才成为停止规则。睡眠等活动用独立作息策略与静默时段，不套用每小时询问。

到检查点提供三个简短动作：

- “这段一直在做，继续”：确认从上次确认点到指定当前时刻的连续投入，更新 confirmedThrough，并延后下一检查点。
- “已经结束”：用户指定实际结束时刻，或直接确认刚刚结束；保留输入精度，修正同一条记录。
- “记不清”：继续保留待核对；也可记一个大致时长，按原规则作为待定位估记单列。

不回复时停止外推“本段暂计”，状态转为 review_required；保留原始开始、检查点和后续操作时间作为回忆线索，不把检查点写成真实结束，也不默认之前 60 分钟全部属实。读取和写入时根据持久化 reviewDueAt 判断到期，正确性不能依赖后台定时器或消息是否送达。关闭推送只改变通知，不关闭未确认时长隔离。

每条活动在得到回应前最多发一次检查点提醒；主动检查点提醒初始最多每日三次，允许关闭，并遵守静默时段。未发送或漏看的提醒合并到晚间对账或下一次打开页面。bot 调度仍是接入条件，不能假定网页关闭后浏览器定时器可靠运行。

数据约束：计时活动新增
`confirmedThrough`（可空）、`reviewDueAt`（可空）、`reviewReason`
和原始操作回执。已核定前缀为
`[startedAt, confirmedThrough)`，没有确认则前缀为空；其后是暂计/待核对部分。明确区间的手工补记、已确认睡眠和接纳后的历史导入，confirmedThrough 等于区间结束；新计时初始为空。确认整个连续前缀需用户明确表达期间一直在做；仅点击关闭提醒、稍后提醒或“我现在正在做”不能证明此前整段连续。期间有中断时不扩大前缀，改用已有修正/补记入口。估计精度独立保存。

切换到下一活动仍在一个事务内释放旧计时槽并开始新活动。旧记录的截断时刻只是候选结束上界，未核定部分留作草稿；不阻塞新活动，也不因开始新活动自动确认之前一直在做。此类 review_required 是记录质量问题，与跨系统写入未知的 pending_reconcile 不同，不能借用后者的全局计时阻塞规则。

成功回执可包含
`ACTIVITY_REVIEW_REQUIRED`、activityId、activityVersion、候选范围和修正入口。明确停止且本段未到检查点、没有异常标记时，可以把这次停止作为用户核定；到期后、异常情况下的停止只关闭草稿，需要用户核对真实结束。日对账支持一次确认多条正常草稿；冲突记录不能盲目批量通过。

例：09:00 开始看书，09:30 实际离开却忘停，10:00 检查点未回应，12:00 开始散步。系统保留“09:00–12:00 看书，待核对”的候选，不记三小时正式阅读。用户说“09:30 就结束了”，原记录变成已核定的半小时；其余时间仍未核定，散步计时不受影响。若 10:00 曾明确确认此前一直在看书，则仅已确认的一小时进入正式统计，之后仍待核对。

修正携带旧 activity 的版本，只修改旧记录；早于原 confirmedThrough 的修正属于明确更正，应同步减少正式总量并保留修订。旧记录不得越过下一条已核定区间。整段都未核定时可将原记录原地转成估记；已有核定前缀时，在同一事务中把原记录结束于 confirmedThrough、撤下其未核定尾段候选，并创建一条关联该修正操作的尾段估记，保证重试不重复创建。检查点确认与新活动切换并发时以 sessionVersion/activityVersion 拒绝过期请求，不能重新启动已关闭的旧活动。

同一任务重新开始时，仅在 Time 活动仍正常 running 且未到检查点的情况下采用“已经在计时”的无变化分支。旧活动已待核对时，新的开始意图应创建当前时刻的新段，旧段保留草稿；不能因为 taskUuid 相同就自动跨越未知空档续记。重复投递同一幂等键仍返回原结果。

锁屏、无鼠标操作、浏览器关闭等信号今后只能用作建议结束点，不能自动认定实际停止：阅读、思考和线下活动也可能没有设备输入。V1 不依赖设备监控。

### 5.3 手工计时安排：主动开始，先到的限制停止

用户已确认示例：预计 60 分钟、计划 14:00 开始、最晚 15:00 结束；13:40 提前开始，应在 14:40 自动停止。采用“本次剩余时长”和“绝对最晚停止时刻”同时约束，先到者生效。此规则只授权自动停止 Time 计时，不授权自动开始、修改 Taskwarrior
start/status/due 或完成任务。

**最小数据契约。** `TimingPlan` 保存
`id/taskUuid?`、`allowanceSeconds?`、`plannedStartAt?`、`hardStopAt?`、`timeZone`、`version`。均在 Time 存储，绝不把 hardStopAt 写入任务 due。任务总体预估可为 allowanceSeconds 提供初值，但一个任务可以有多次独立安排；本次消耗不直接扣减任务全部历史预估。设置本次时长或 hardStopAt 即启用相应停止限制；两者皆空时沿用 §5.2。

计划开始只供展示和可选提醒，不构成开始门槛。允许提前、准时或晚开始，实际 startedAt 一律取明确开始动作的服务端执行时刻，不回填 plannedStartAt。用户没有开始时，计划开始提醒、计划结束、另一项结束、刷新、恢复备份或服务重启都不得创建 Activity。系统没有 auto_start 工具或自动触发分支。

开始时的剩余额度 R =
allowanceSeconds 减去本 TimingPlan 已消耗的计时段时长；暂停空档不计，草稿中已计时部分也计入额度，不能因为尚未核对而获得无限新额度。已关闭区间、当前段和修正使用同一事务口径；更正活动时长后调整额度并保留审计，但更正、删除或撤销不会自动重启计时。同一安排的历史段不重复计算。

活动开始时保存 R 与规则版本的快照。修改历史记录会更新本次安排的剩余额度/超出额度提示，但不悄悄移动已显示的当前 autoStopAt；若需改变当前段的停止时刻，显式应用新的限制版本。下一次手动开始使用更正后的剩余值，不能沿用旧快照。hardStopAt 始终有效，历史修正不等于获准越过它。

```text
durationStopAt = actualStartedAt + remainingSeconds   # 配置了额度时
autoStopAt     = min(durationStopAt, hardStopAt)       # 只取存在的限制
```

R <= 0 返回 `TIME_ALLOWANCE_EXHAUSTED`；当前时刻 >= hardStopAt 返回
`TIMING_PLAN_EXPIRED`，均为未执行的 409，不创建零长度记录。plannedStartAt >=
hardStopAt 的计划配置拒绝保存；额度比计划窗口长则允许保存，但明确展示此次可能被窗口截短。只有计划开始而没有停止限制时不会据此发明截止时间。

| 条件（额度 60 分钟，计划开始 14:00，最晚 15:00） | 结果                                                  |
| ------------------------------------------------ | ----------------------------------------------------- |
| 13:40 开始，无中断                               | 14:40 停止                                            |
| 14:00 开始，无中断                               | 15:00 停止                                            |
| 14:30 开始，无中断                               | 15:00 停止，只计 30 分钟                              |
| 14:00 开始，14:20 暂停，14:40 手动继续           | 剩余额度 40 分钟，但 15:00 先到；本次安排累计 40 分钟 |
| 原安排耗尽后再次点开始                           | 不重置额度；明确增加额度或新建安排后再手动开始        |
| 15:10 点原安排的开始                             | 已过最晚停止；必须明确修改安排或创建新安排            |
| 整段从未手动开始                                 | 到期标记未开始/已过期，任务仍保持原状态，无时间流水   |

**暂停和延期。**
暂停/手动停止关闭当前段，不移动 hardStopAt；再次手动开始沿用剩余额度。新安排需要明确创建，不因午夜、任务仍未完成或重复点击自动刷新额度。对运行中安排修改限制必须带 planVersion、sessionVersion，预览新的 autoStopAt 后显式应用；只改任务预估模板不影响当前计时。增加额度不能隐式越过 hardStopAt，若要越过还须修改硬性时刻。把停止时刻移到过去的请求拒绝为历史修正歧义，可选择“现在停止”或单独修正过去记录。

**到期生命周期与核对分离。** Activity 增加
`timingPlanId`、`autoStopAt`、`limitVersion`、`timerStoppedAt`、`stopReason` 和
`processedAt`；lifecycle 的 open/closed 与记录质量的待核对状态分开。到期在事务内以 autoStopAt 关闭计时并释放当前槽，stopReason 为 duration_limit、hard_deadline 或 both_limits；confirmedThrough 不因自动停止向前移动，未核定段保留为草稿。此前已经确认的部分继续有效。任务可以仍显示“进行中”，时钟必须显示“已按规则停止”。

配置了自动停止的活动默认不再叠加普通 60 分钟检查点，减少打扰；用户若另设中途检查点，忽略它也不能取消后续自动停止。自动停止后的默认动作是“确认这段 / 实际提前结束 / 增加时间并手动继续”，不会自动延时，也不自动接下一任务。到期后点击“继续”是新的明确开始动作，默认从点击时刻生成新段，不填补中间空档；若硬性时刻已过，先明确调整安排。

真实投入可以少于也可以多于自动计时。用户事后明确说“我实际做到 15:10”时，允许按已有修正/补记流程记录超出的实际投入并标注超出本次安排，保留原 timerStoppedAt/stopReason 事件；不篡改停止规则来假装当时一直在计时，也不限制如实记账。修正若与另一条已核定活动重叠仍须解决冲突。

**可靠停止。**
实际开始事务持久化 autoStopAt 和限制版本，服务端根据数据库建立到期队列；后台调度负责及时结算，通知是否送达不参与停止判断。所有读取都按 min(now,
autoStopAt) 截止暂计，所有计时相关写入先幂等处理已经到期的当前活动。服务迟醒或重启后以原 autoStopAt 作为 timerStoppedAt，以处理时刻作 processedAt，禁止补算到重启时间。打开网页或补结算不能自动续计。

后台截止动作只针对匹配的 activityId、timeEpoch、limitVersion；重复触发无额外效果，旧定时器不能停止已延期或已切换的新活动。延期与截止并发时按事务顺序决定：延期先提交使旧版本截止失效；截止先提交则原段已关闭，后续延期不能复活它，需要明确开始新段。暂停不生成新时长，延迟收到的旧开始请求仍受幂等、版本和截止校验约束。

跨系统 pending_reconcile 不能让已经持久化的 Time 活动超过 autoStopAt。可关闭已知活动并保留待核对依赖；若这使原协调操作的活动版本过期，转为核对，不能盲目补完并重开旧时钟。恢复独占期间后台写入仍遵守 gate；读取/显示上限和恢复后的补结算保证不多算，不能为了准点写入绕过恢复锁。

时区只影响计划时间解析和展示，autoStopAt 存绝对时间；明确跨日日期，DST 歧义沿用日期校验规则。客户端墙上时钟跳变不能修改服务器停止时刻。服务器校时异常时保留诊断与待核对状态，不声称离线期间已经准确感知人的活动。

**通知边界。**
自动停止是服务端业务动作，bot 只读取停止事件并通知。每个停止事件仅通知一次，使用独立于每日检查点提醒上限的事件去重键，并遵守静默时段；延迟消息写明实际停止时刻。服务器离线可能导致通知延迟，但不能导致账本超过持久化上限。既有 bot 接入未完成时，网页仍能展示正确的截止状态。

## 6. 任务兼容不靠双写碰运气

Time 原生 API 的 taskUuid 只是关联：`time_start(taskUuid)`、`time_stop`
不改变 Taskwarrior 的 start、status、due 或 UUID。

现有任务接口保持任务语义，并通过服务端协调器连接同一个 Time 引擎：

| 明确的用户操作               | Taskwarrior 效果           | Time 效果                                         |
| ---------------------------- | -------------------------- | ------------------------------------------------- |
| 原生开始活动，可带任务引用   | 无写入                     | 开始/切换唯一主活动                               |
| 原生结束活动                 | 无写入                     | 关闭指定的当前活动                                |
| 既有 task_start(A)           | 按既有语义 start A         | 成功后开始/切换到 A；已在计时 A 时不拆成重复区间  |
| 既有 task_stop(A)            | 按既有语义 stop A          | 只关闭关联 A 的当前活动，不停止正在计时的 B       |
| 既有 task_complete/delete(A) | 执行用户明确请求的任务动作 | 成功后关闭关联 A 的当前活动；历史保留任务名称快照 |
| 修改时间记录、预算或未来计划 | 无写入                     | 仅修改 Time                                       |

开始 B 不会隐式 stop/完成 A 的 Taskwarrior 状态。任务“进行中”与“正在计时”是两个不同事实，Web 的 Time 控件读取当前 activity，不用 task.start 推测运行中的时钟。

由于外部 Taskwarrior 命令与 SQLite 不共享事务，协调器必须持久化 operation：

1. 在持久化操作表记录幂等键、任务动作、操作前状态、期望当前活动版本和固定的有效时间；暂时占用该工作区的计时协调槽。
2. 执行既有任务命令。确认成功后，在一个数据库事务中应用 Time 变化并保存成功回执。
3. 明确未执行时标记失败，不改 Time；任务动作可能已执行但响应或账本落盘失败时标记
   `pending_reconcile`，不返回完整成功。
4. 重启后和继续计时前，依据持久化操作记录核对任务与 Time。证据足够才完成该操作缺失的本地步骤；存在外部修改或无法确认时保留待核对，不再次盲目执行任务命令。
5. 未解决的跨系统操作仅暂停相关计时切换，不把无关的任务列表、看板和 Time 历史读取全部锁死。后台不可能在不核对的情况下保证跨系统恰好执行一次。

服务端统一入口能覆盖使用 HTTP/Socket 的既有客户端。直接调用原生 CLI、脱离服务端的桌面本地模式和外部 hook 不在捕获范围内；不从其 start 标记猜测实际活动。启用前枚举实际使用的入口并验证，不能宣称已覆盖四端。

桌面/TUI 不新增 Time 页面，但须进行最小兼容：取消或按能力字段绕过旧硬拦截、展示不确定写入、避免误停其他活动。旧版本客户端继续使用限制必须明确，不能只改新 Web 后宣布全面兼容。

### 6.1 已开始任务、未知结果与操作依赖

协调器持久化至少包含：`operationId/idempotencyKey`、规范化输入摘要、`taskDataEpoch/timeEpoch`、`targetTaskUuid`、操作前任务快照（status/start/modified）、`preActiveActivityId/preSessionVersion`、固定
`effectiveAt`、`externalDisposition`、`state`
和最终回执。任务 start 非空不是操作身份，modified 也不是唯一执行凭证。

| 分支                                          | 外部任务命令                                   | Time 处理与恢复依据                                              |
| --------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------- |
| 未完成的 A 已有 start，当前计时 A             | 跳过重复 start，记 `skipped_already_satisfied` | 返回幂等无变化结果，不重开区间                                   |
| 未完成的 A 已有 start，当前为 B 或空          | 跳过重复 start，记 `skipped_already_satisfied` | 经当前活动版本检查，直接在 Time 事务内切换到 A                   |
| A 尚未 start                                  | 记录 prepared 后执行一次命令                   | 明确成功先持久化 `acknowledged`，再完成本地账本步骤              |
| 命令可能已执行，但确认未持久化                | 不重发                                         | 进入 pending_reconcile；读取任务仅提供核对证据                   |
| 已持久化 acknowledged 或 skipped，Time 未完成 | 不再执行任务命令                               | 代次、依赖版本及任务有效性仍匹配时，可补完本地步骤，否则继续核对 |
| A 已完成、删除、消失或发生不可解释的状态变化  | 不隐式重开或创建                               | 返回冲突，保留原意图供用户重新决定                               |

preState 读取、判断和依赖预留在同一个协调器调度范围完成。已有 start 时不再依赖“命令前后 start 是否变化”。对于原来没有 start 的未知命令，后续看到 start 非空甚至 modified 变化，也不能证明本次执行成功：可能来自外部 CLI、其他操作或恢复。此时可提示“任务现在已开始，是否接纳这笔计时”，但不能仅凭这两个字段自动写成功回执。

`prepared → external_acknowledged/skipped → applied`
为正常路径；存在不确定外部结果时转
`pending_reconcile`。操作状态持久化失败也按未知处理。始终不把 SQLite 事务跨越网络/子进程 await；Taskwarrior 写队列只进入一次，避免持有它再递归调用 runner.write。

统一锁顺序为工作区 gate 许可 → 协调器依赖预留 →
Taskwarrior 写队列（如需要）→ 短 SQLite 事务。每一笔请求结束均释放内存许可，待核对状态由持久化记录维持；恢复独占锁不会被等待用户回复的操作长期占住。

依赖集合至少包括目标任务、操作前活动及其关联任务、当前计时槽。未完成操作冻结这些依赖和全局计时切换，不能冻结所有任务写入。A 既不是当前活动的任务，也不在任何待核对操作的依赖集合内时，complete/delete(A) 直接走原任务动作，无需获得计时槽；返回
`timeEffect: none`。若任务 B 的未知切换涉及 A 的旧活动，则 A 属于依赖，不能仅用
`activeActivity.taskUuid !== A` 判定无关。

与当前活动有关的 complete/delete 必须继续使用协调器。无关任务动作仍经过已有任务队列和工作区 gate；恢复进行中时不能绕过 423。V1 不承诺捕获绕过服务端的原生命令并发，发现不一致即核对。

## 7. Timewarrior 只做冻结历史导入

启用 Time 记录切换点 C，之后新数据以 Time 为准。已有 Timewarrior 文件和 Taskwarrior 数据保留。旧 hook 可能继续产生副本，但不作为 Time 的读取依赖，也不能再次导入 C 以后的副本。

首次启用发现正在运行的旧计时时，展示现状，让用户选择延续哪一条或从当前时刻开始。历史部分与新活动在 C 衔接，保留迁移关联，不假装发生了实际休息。多个任务 start 标记不能自动生成多个活动，也不能为统一时钟自动停止其他任务。

历史导入采用：固定导出文件 → 摘要/范围/冲突预览 → 接纳导入。保存快照校验和、批次 UUID、原始记录、裁切范围与每条新 activity
UUID 的映射。

同一个冻结快照中的记录序号可以用作批内定位；它不等于 Timewarrior 跨导出的稳定 @id。重复提交同一批次返回原结果。不同快照覆盖同一历史范围时，先预览差异和本地修订，不自动追加或覆盖。导入时发现重叠记录先隔离为候选，不加入主图。

Time 内的历史修正保留来源与修订，不回写 Timewarrior。由此避免追踪源端移动、拆分、合并后身份漂移的复杂同步系统。

## 8. 独立 SQLite 存储、版本与备份

选用工作区数据目录下的
`time.sqlite`。活动、策略、分类映射、当前计时、操作回执和导入批次同库事务处理；不采用按月 JSON 分片，避免跨午夜、跨月切换需要多文件事务。

采用
`node:sqlite`，与现有服务端的无第三方运行时依赖方向一致，现有 sqliteSnapshot 可复用在线备份与完整性校验思路。模块通过最小存储适配层访问数据库。上线前锁定实际 Node 小版本并验证 API、迁移和恢复；Node
22 分支使用 backup() 的最低版本为 22.16.0，不能沿用笼统的“Node
22+”或仅验证 DatabaseSync。

此前本地验证仅证明 Node
v24.21.0 可创建内存数据库并执行查询，不证明 dmit 已具备运行条件。仓库现有 backup() 用法说明已经有相同依赖，不代表生产运行时版本已核实。部署预检需要使用实际运行服务的 Node，执行一次临时数据库备份及 integrity_check 后清理临时文件。

版本边界：activity 有行版本；当前计时有独立 session 版本；策略有 policy 版本。与 organization.revision 无关。同一时间范围内的并发补记仍须在数据库事务内重新检测重叠，不能仅凭行版本绕过。

传输继续走现有 HTTP/Unix Socket 与认证、source
identity 和工作区恢复闸门。独立 revision 只隔离业务冲突，不绕过恢复独占锁，也不新增一个未经保护的写入口。持久化的待核对计时操作不长期占住全工作区锁。

Time 接口独立读取日期范围和索引，不调用 organization.load/change。关联任务只按需解析并缓存展示信息，失效时仍可展示已存快照。Time 不再让每笔记账都全量导出 task/timew。现有组织接口自身的性能改善另行评估，不混入首版。

备份必须覆盖数据库、策略、操作回执和导入清单。提供独立 Time 导出/预览/恢复，不塞进旧 8
MiB organization 备份载荷。界面明确旧 Aster 备份不包含 Time。

备份采用数据库一致性快照或维护锁下的完整快照；若启用 WAL，不直接复制单个打开中的 .sqlite 文件。恢复前停止 Time 写入、保存恢复前副本、校验 schema 和来源，恢复后核对操作日志。恢复出的打开活动进入待核对状态，不能自动累计服务器停机期间的时长。

恢复旧快照还必须处理幂等回执回退：以恢复代次和时间屏障隔离旧请求，丢弃/人工核对屏障前的迟到消息，不因旧回执不存在就重新记账。关联任务数据分别恢复时，缺失任务保留历史快照，不自动重建任务。取消 Time 功能时保留可读导出，不把新账本自动反写成 Timewarrior 历史。

### 8.1 发版备份必须包含 Time

`deploy/deploy.sh`
的备份清单增加 time.sqlite 及 Time 恢复代次/屏障元数据。不能仅扩大 JSON 备份循环，也不能复制活动数据库的单个文件。发版脚本、独立 Time 备份与恢复前备份使用同一套 SQLite 快照和校验实现。

执行顺序固定为：

1. 预检实际运行方式（容器或 systemd），使用该服务的 Node 与数据路径，不因为宿主机存在另一个 Node 就优先使用它。确认 DatabaseSync、backup、目标目录权限、空余磁盘及 schema 支持。
2. 服务正常运行时，通过受保护的内部维护入口进入 gate.exclusive，排空服务管理的任务和 Time 写入，再顺序备份原有 JSON、Taskwarrior
   SQLite 和 Time
   SQLite。只在这个短检查点阻塞新写；不把构建或上传放进锁内。该入口与恢复入口都不能持有同一 gate.enter 许可再等待 exclusive，内部快照助手也不再次 enter；采用既有恢复流程的“前置许可释放后进入独占”模式。绕过服务端的原生 CLI 写入需在维护窗口暂停，SQLite 单库在线备份本身不保证多个存储同时一致。
3. 快照先写入数据目录内的唯一临时目录（如
   `/opt/aster/data/backup-staging/<backupId>`）。systemd 模板的 ReadWritePaths 允许数据目录，不允许假设服务能写
   `/opt/aster/backups`；容器路径也需与已挂载数据目录一致。内部入口不接受任意输出路径。
4. `await backup()`，在 finally 关闭连接；用新连接执行完整性校验，读取 schema/代次，记录字节数与校验和。全部文件完成后发布完成清单，释放检查点。脚本再把封闭的快照搬到 REMOTE_BACKUP 并复核清单，不依赖跨文件系统 rename 的原子性。
5. 清单至少包括 backupId、releaseId、source
   identity、创建时间、每个数据文件的存在状态/校验和/大小、Time
   schemaVersion/timeEpoch/taskDataEpoch 和当前计时/待核对操作摘要。临时文件不能被识别为完成备份。
6. Time 已启用而数据库缺失、运行时不支持 backup、校验失败或超时，必须在切换版本前退出；服务恢复接收正常请求，旧发布保持运行。尚未初始化 Time 时明确记录
   `time: not_initialized`。Time 已禁用但文件仍存在时仍备份，不能当作未初始化跳过。

首次升级的旧服务可能没有内部检查点入口。此时先上传构建产物，再用短维护窗口停止受管理的写入进程、执行同一快照助手、校验成功后切换重启；失败则启动旧发布。容器已停止时不能再 docker
exec，须用相同镜像及数据挂载运行维护助手；systemd 使用配置中的实际 Node。没有可验证的运行时就中止。不能因旧服务不支持入口就悄悄略过 Time 备份。新接口沿用本地 Socket 的认证/source 校验，不新增公网维护端口。

数据库迁移只在完整备份已确认后执行。健康检查需要覆盖 Time
schema 可读及恢复屏障已加载，不能只以 HTTP
200 代表 Time 可用。自动回滚前校验旧发布是否支持迁移后的 schema；不支持时禁止让旧程序写新库，也不能直接还原发版前快照丢弃上线后的新活动。V1 优先使用兼容旧版本的增量迁移；非兼容迁移保留维护状态并走明确恢复方案。

systemd 文件中的 MemoryMax=192M 只是该模板的限制，容器实际限制须另查。预发布同时运行记录写入、周报查询和在线备份，记录峰值内存与耗时；在 192
MiB 配置下先以至少 32
MiB 峰值余量为发布门槛，超出则优化分页、范围查询与备份批次后重测，不默默修改线上内存限制。该门槛是待验证的工程预算，不是已测结果。

### 8.2 旧任务恢复与 Time 的核对钩子

旧 Aster 备份载荷仍不包含 Time，旧链路对原生运行计时的停止要求也保留。新增的是恢复前后的依赖协调，不把 time.sqlite 加进旧原生文件替换列表。Time 独立备份/预览/恢复不调用 recovery.export、nativePaths 或 Timewarrior 可用性检查。

旧恢复预览同时展示 Time 影响：关联任务的打开活动、待核对操作及将暂停的记录。预览令牌绑定
`timeEpoch/taskDataEpoch/sessionVersion/pendingOperationRevision`；任一变化时需重新预览，不能在准备阶段和实际交换之间漏掉新计时。

恢复顺序与崩溃处理：

1. 在 applyPrepared 的最终 gate.exclusive 内再次校验原生指纹和上述 Time 版本。所有 HTTP/Socket
   Time 写入和后台修改均须持有 gate.enter 许可；独占恢复开始后新请求得到 423，已有请求排空。被独占函数调用的内部钩子不再次 enter，避免拒绝自身或死锁。
2. 在移动任何原生文件前，将 restoreId、Time 核对要求和恢复阶段写入现有恢复 manifest，并在 Time 中幂等执行
   `prepareTaskRestore(restoreId)`：生成新的 taskDataEpoch，失效旧任务操作预条件，冻结关联任务的当前活动至固定
   `suspendAt`。恢复标记必须在文件交换前持久化；写失败则不开始交换。
3. 冻结不删除历史，不猜测实际停止时刻。被影响的打开活动标记 review_required，候选显示不越过 suspendAt，正式统计仅保留原 confirmedThrough；用户后来可确认结束时间，或从确认时刻创建新的继续记录。与任务无关的活动不因任务恢复自动终止。
4. 执行既有原生文件交换/回滚逻辑。得到明确的 committed 或 rolled_back 结果后，按 restoreId 调用
   `finalizeTaskRestore`
   核对引用：任务消失/完成/删除时保留历史快照和失效关联；任务被重开或 start 变化时保持待核对。即使当前状态看似相同，也不能替用户自动续计或重新执行旧 pending 操作。
5. taskDataEpoch 在回滚时也不退回旧值。受影响 pending 操作标记
   `TASK_DATA_EPOCH_CHANGED`
   并保留原回执供检查；无关任务读写在原生恢复完成后可继续，计时槽有待核对依赖时仍阻止切换。
6. 原生文件已提交但 Time 核对失败时，报告“任务恢复已完成，时间记录待核对”，持久化剩余工作。不要因为后置钩子异常进入原生交换 catch 并再次回滚 Taskwarrior。Time 写入在屏障未完成时关闭，任务只读服务可保留；无法确定原生恢复结果时沿用已有整体恢复保护。
7. 启动顺序为原生 repair
   → 重放未完成的 Time 恢复核对 → 开放正常计时写入。不能只扫描 prepared
   manifest：committed/rolled_back 但 Time 钩子未确认的 manifest 也要处理，restoreId 去重避免二次冻结。崩溃发生在标记与 Time 事务之间时，依据 manifest 先补齐屏障，禁止先运行旧 pending 操作。

restoreId 标记位于旧恢复目录、不会随被还原的 Taskwarrior/organization 文件回退；Time 自身恢复还需使用不随数据库回退的恢复屏障。manifest 路径白名单与原生 repair 的校验保留，不能让钩子接受备份提供的任意路径或执行指令。

用户核对只提供明确动作：确认结束并修正旧记录、从当前时刻继续、或为新的活动解除失效任务关联。均是带版本的新操作，不篡改任务状态；历史引用快照继续保留。

## 9. bot 负责调度，Aster 负责摘要和写入规则

链路：bot 的定时调度 → 调用只读 `time_reconcile_digest` →
bot 根据用户设置发消息 → 回复经 MCP 写入。MCP 本身不是推送调度器。

Aster 返回明确的日期/时区、候选标识、值得询问的空白、数据版本和可展示摘要，不主动发送通知。bot 负责用户和会话绑定、提醒时间、静默时段、当天是否已发送及发送失败处理。每日最多一次合并对账提示，不对每段空白分别打扰；可关闭的活动检查点提醒使用 §5.2 的独立次数限制与去重键。到期停止由 Aster 自己执行并保存事件，不能交给 bot 轮询结果决定是否停止，也不能用计划开始提醒自动调用开始工具。

不能假定用户已有 bot 实现了这些能力。先核实 bot 仓库与部署；调度没接通时，网页对账和手动询问仍完整可用，主动通知明确标记未接通。

写入契约：

- 幂等身份至少包含 workspace/source、会话、原始消息 ID、逻辑动作编号。同一消息的规范化输入及解析结果先持久化，重试复用，不能每次重新让模型拆出不同动作。
- 同一个键、相同输入返回原回执；同键不同输入拒绝。编辑消息或纠错使用新的显式修正操作，并引用原 operation/activity。
- 记录
  `receivedAt`、用户时区和明确目标日期。相对日期依据原消息上下文解析，跨午夜重试不漂移。凌晨的“昨晚”有歧义时问明确日期，或展示候选让用户选择，不能套用财务记账日猜测。
- 提供
  `operation_get`。结果未知时先查询，不由模型重复提交；Time 原生操作在其事务和幂等记录可证明结果后，可复用同一个键取回结果。跨系统操作遵循前述待核对流程。
- 撤销是一笔带版本检查的新操作，只作用于原操作仍匹配的记录。原记录已被其他客户端改过时返回冲突；不重放整个旧快照覆盖后续工作。撤销 Time 记录不自动撤销已经完成的任务动作。
- bot 发送端自身也需持久化发送状态；平台不支持发送幂等时，不宣称网络结果未知情况下能保证提醒恰好一次。

### 9.1 平台消息编辑的适配契约

bot 持久化
`平台/会话/作者/messageId → 原 operationId、activityIds、各记录版本、原 receivedAt/时区、已处理编辑版本`
的映射。没有这份映射时先查询或提示无法关联，不能将编辑事件当作新的创建消息。

收到平台编辑事件时，使用独立的 eventId 或单调 editRevision 构造新的幂等键，并引用原操作。平台仅给 editedAt 时同时保存内容摘要用于去重；版本先后不能可靠判定时不自动覆盖，转为核对。重复编辑事件返回原修正结果，旧版本乱序到达不覆盖较新编辑。

修改文字、分类、估计时长或明确区间，转成
`time_update(activityId, expectedVersion, patch)`；明确撤销才调用 time_undo。原始输入内容仍保留作审计。编辑消息不会再次执行“开始活动”、再次切换时钟，也不会自动撤销已执行的 Taskwarrior 动作。

原消息仍是 pending_reconcile 时先处理原结果；已被网页或另一条消息修改过的活动发生版本冲突时显示差异，不刷新版本后强行覆盖。原消息生成多条活动且新文字不能一一对应，或编辑改变动作类型时，给出待确认的变更清单；V1 不实现猜测式批量替换。

相对日期沿用原消息的参考日期与时区，不因次日编辑漂移。“昨晚”改成另一个相对时间而含义有歧义时，展示具体日期再核对；明确写出的新日期可正常修正。平台删除消息不隐式删账，除非用户另行明确撤销。

编辑能力只向能提供可靠消息身份且已绑定正确用户/工作区的平台适配器开放；没有编辑事件的平台仍支持“把刚才那笔改成……”的显式修正入口。

| REST-02  | 恢复后关联任务消失、完成、重开                    | 历史保留，受影响活动不自动续计，旧 pending 不自动重放                             |
| REST-03  | 分别在交换前、交换中、提交后钩子前崩溃            | repair 后都执行幂等 Time 核对；未核对前不开放计时写入                             |
| REST-04  | 原生提交成功但 Time 后置钩子失败                  | 明确部分结果，不二次回滚任务数据；重启可完成余下核对                              |
| REST-05  | Timewarrior 不可用，执行独立 Time 备份恢复        | 无 Timewarrior 前置依赖；校验、恢复代次及旧消息隔离仍有效                         |
| EST-01   | 两条估记窗口同为 19:00–21:00                      | 就地注释展示，C/U 不变；定位一条只改原 UUID，另一条不变                           |
| EST-02   | 窗口跨日、与已有区间重叠或跨多个空白槽            | 不重复统计、不暗示已占时间；定位冲突保留输入                                      |
| BOT-01   | 编辑同一个 messageId 并重放编辑事件               | 只产生一次带版本的修正，不再次创建/开始活动                                       |
| BOT-02   | 编辑乱序、跨午夜、原记录已在网页修改              | 不覆盖新版本、不漂移日期；有歧义或冲突明确核对                                    |
| BOT-03   | 编辑原结果未知的消息，或删除聊天消息              | 先核对原操作；删除消息不隐式删除账本                                              |

相关代码落点：部署与运行时在 deploy/deploy.sh、deploy/aster.service 及 sqliteSnapshot，实施时同步服务端与部署文档的最低运行时要求；计时协议在 core/workspace、server 与各客户端 DTO；恢复钩子在 backup-restore、workspace-gate 和服务启动顺序；消息编辑在实际 bot 适配器，MCP 只提供带版本的修正接口。以上均是待实现清单，本轮未修改这些业务文件。
